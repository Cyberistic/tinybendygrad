==============================================================================
ptx.py writes `shl.b{name[1:]}`, `xor.b{name[1:]}`, `and.b{name[1:]}`,
`or.b{name[1:]}`. The suffix is the dtype name with its FIRST CHARACTER
removed, so `pred` -- `types[bool]` -- becomes `red`:
   types[bool  ] = pred -> name[1:] = red  -> shl.bred

   types[u8    ] = u16  -> name[1:] = 16   -> shl.b16

8. THE SEVEN CONSTANTS THE CONSTANTS SWEEP COULD NOT SEE, CROSS-CHECKED
==============================================================================
`fn_kp`'s ASCII bounds are the sweep's whole blind list for this file, and a
blind list is only honest if the constants in it were checked SOME OTHER WAY.
CPython's own set is `string.ascii_letters + string.digits + '_'` (helpers.py:156):

   CPython keep-set : 63 code points
   ptx.bend fn_kp   : 63 code points
   MISSING from the port : none
   EXTRA   in the port   : none

and the boundaries in hex, so a transposed digit pair would show:
   48='0x30' 57='0x39' | 65='0x41' 90='0x5a' | 97='0x61' 122='0x7a' | 95='0x5f'
Every one is the CPython value. The sweep could not see them because no fixture
input contains a character ADJACENT to a bound -- `a-b` and `x$y.z` sit INSIDE
the ranges, and only M05 (or-not-and) and M06 (low-nibble-first) move them. That
is a FIXTURE gap with a cheap close: one more `to_function_name` input holding
`~` (126) and one holding `/` (47) would move six of the seven on a `+1`.
