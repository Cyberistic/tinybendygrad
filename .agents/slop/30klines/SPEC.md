# 30klinesofcode — specification

Status: design, 2026-11-09. Nothing here is built yet.
Companion: `AGENT-BRIEFS.md` (how to split the work). Mockups: `mock/`, renders: `art/`.
Line census: `count.py`, re-runnable, prints every bucket it counts.

---

## 1. What it is

An interactive course that walks tinygrad's source line by line, using one eight-line program as
the spine. The learner reads real code, runs it, and watches the graph change at every stage.

The promise is narrow on purpose:

> Every claim is pinned to a line of real source. Every picture is generated by running tinygrad.
> Nothing is drawn by hand.

That is the whole product. Everything below exists to keep those two sentences true.

The name is a slogan, not a measurement. The build publishes the real census, and every number a
learner sees comes from a generated manifest. A hand-typed "30,000" is a lie that rots.

## 2. The measurement (this is the first design decision)

Two counters exist and they answer different questions. The canonical one is **`sz.py`**, tinygrad's
own: distinct lines carrying a token, docstrings excluded, `runtime/autogen` and `viz/assets`
skipped. It is the project's definition of its own size, so it is the denominator. `tools/census.py`
loads `sz.py` by path and calls `gen_stats` — it does not re-implement the rule, because a second
copy of a counting rule is exactly the thing that rots.

    uv run --no-project --with tabulate --with numpy --python 3.12 \
      python .agents/slop/30klines/tools/census.py

One reading, 2026-11-09, `tinygrad@6295132e`:

| group | lines |
| --- | ---: |
| `runtime` | 7,303 |
| `renderer` | 3,629 |
| `uop` | 2,581 |
| `llm` | 2,338 |
| `viz` | 2,069 |
| `codegen` | 1,817 |
| `mixin` | 1,698 |
| `nn` | 1,438 |
| `schedule` | 1,136 |
| `helpers` · `device` · `engine` · `tensor` · `dtype` · `function` · `__init__` | 2,097 |
| **total** | **26,106** |
| core (excludes llm, nn, renderer, runtime, viz) | 9,329 |

`count.py` is the second reading, and it answers a different question: raw lines with comments and
blanks separated, over **this repo's** pinned tree — 34,511 total, 24,600 code, 12,885 in the
spine. Keep both. Quote neither without naming the tree and the rule that produced it.

The course vendors `6295132e` in `references/tinygrad-latest` and cites that tree only. A lesson
whose ref does not match it fails the build; one line of mutation is enough to red it.
The figures drawn in `mock/` are from the earlier `count.py` reading and are illustrative; the
live numbers are `content/census.json`, regenerated by `tools/census.py`.

Populations, so the numbers cannot be argued with later:

- **spine** = `tensor.py`, `mixin/`, `uop/`, `dtype.py`, `device.py`, `schedule/`, `codegen/`,
  `renderer/`, `engine/`, `helpers.py`.
- **outside** = `runtime/`, `nn/`, `llm/`, `viz/`, `examples/`.
- **excluded entirely**: `runtime/autogen/` — about 180k lines of generated PCI and register tables.
  A naive `cloc` says 271,709 lines for `tinygrad/`; that number is worthless and must never appear
  in the product.

Three consequences the design has to absorb:

1. **`mixin/` is 1,698 by sz.py's rule, and it is mostly docstring.** The operator table's prose is
   longer than its code, so a per-line walkthrough there would be padding dressed as rigour.
   Lessons there explain the table and the broadcast rules, not every signature.
2. **`uop/ops.py` alone is 1,524 lines** — 16% of the core in one file. It gets its own sub-arc,
   not one lesson.
3. **`runtime/` (7,303) plus `renderer/` (3,629) is 42% of the tree.** The course cannot honestly
   claim full coverage. It claims coverage of the core, and it says so on every screen.

**The progress bar divides by `manifest.declared`, not by 30,000 and not by 26,106.** `declared` is
the set of line ranges that lessons actually claim, deduplicated by `(file, line)`. Three separate
reads, always shown together:

```
source coverage    4,820 / 26,106 lines
concept mastery    12 / 80
pipeline coverage  2 / 10 stages
```

## 3. Visual language

The first attempt at this looked like a SaaS dashboard, which is the wrong register for a compiler.
The correction is total: **paper, hairlines, monospace, no ornament.** Green is a signal, not a
brand.

### 3.1 Tokens

| token | paper | dark | where |
| --- | --- | --- | --- |
| `--paper` | `#F4F2ED` | `#0B0C0E` | background |
| `--paper-2` | `#EDEAE2` | `#111317` | active row |
| `--ink` | `#16161A` | `#E8E6E1` | text |
| `--muted` | `#6E6A63` | `#8C8A84` | secondary |
| `--faint` | `#9A958C` | `#5F5D58` | metadata |
| `--rule` | `#D6D1C7` | `#23262B` | 1px dividers |
| `--accent` | `#3DA639` | `#4CB53F` | **execution only** |
| `--wash` | `#E4EFD9` | `#16240F` | highlighted source |

Rules that are not negotiable:

- 1px rules. `border-radius: 0` everywhere except chips (2px). No shadows. No gradients.
  No glass. No glow.
- **Green appears only where something ran, is current, or just changed.** Never for branding,
  never for "success" decoration, never as a button fill.
- No icon set. Glyphs only: `→ ← ▸ ✓ × ⋯`. Arrows are text.
- Tabular figures everywhere. Units are small and faint.

### 3.2 Type

- UI chrome: monospace, 10–13px. Labels are 9.5px, letter-spaced, uppercase.
- Prose: a neutral grotesk, 14px/1.7, max 58ch.
- Code: 11–12px, line-height 19px, 4px tab stops.
- The pairing is the point: **mono for the machine, sans for the human.**

### 3.3 Motion and sound

Borrowed from effect.institute, but slower and quieter — this is a compiler, not a slot machine.

| event | motion | sound |
| --- | --- | --- |
| a line is explained | fade + 4px rise, 60ms stagger, 220ms ease-out | 880 Hz sine, 90ms, −24 dB |
| graph node enters | scale 0.92 → 1, 140ms, no bounce | none |
| edge draws | `stroke-dashoffset`, 200ms | none |
| step advances | the highlight slides, 120ms | click, 1 per advance |
| stage changes | cross-fade 150ms | two-tone, 220ms |
| a claim fails to verify | shake 2px, 1 cycle | 220 Hz, 70ms |

All sound is synthesised with WebAudio oscillators. No audio assets — the same rule as the rest of
the project: if it can be code, it is code. One sound per interaction, never on hover.
`prefers-reduced-motion` kills the stagger and the slides; the mute toggle is remembered.

### 3.4 Keyboard

`space` play/pause · `←/→` step · `j/k` move · `g` graph · `p` playground · `/` search ·
`?` shortcuts. Every lesson is completable without a mouse.

## 5. The curriculum

### 5.1 Why not source order

Reading tinygrad top to bottom teaches `Tensor`, then 1,500 lines of `UOp`, then a scheduler the
reader has no reason to want. **The learner needs to see the destination before the machinery.**
So: surface → destination → rewind.

Three acts, ten stages. The order below is the *teaching* order; the numbers are the real code
budgets from `count.py`.

**Act I — the surface (2,301 + 2,566 = 4,867)**

| # | stage | files | answers |
| --- | --- | --- | --- |
| 01 | user space & tensor | `tensor.py`, `mixin/*`, `dtype.py` | what is a Tensor, really? |
| 02 | lazy capture & uop | `uop/ops.py`, `upat.py`, `symbolic.py` | why has nothing run yet? |

**Act II — the destination (602)**

| # | stage | files | answers |
| --- | --- | --- | --- |
| 03 | codegen & execution | `codegen/__init__.py`, `engine/realize.py` | what does this program become? |

This stage is a fast-forward: take `(a + b).relu().sum()` and follow it to two WGSL kernels, a
dispatch, and a number on screen — with every intermediate shown but only cursorily explained. It
exists to give the rest of the course a target.

**Act III — the machinery (7,416)**

| # | stage | files | answers |
| --- | --- | --- | --- |
| 04 | schedule | `schedule/__init__.py`, `multi.py` | which ops belong in one kernel? |
| 05 | rangeify | `schedule/rangeify.py`, `indexing.py` | how does a shape become a loop? |
| 06 | decompose & rewrite | `codegen/decomp/`, `uop/upat.py` | how does RELU become MAX? |
| 07 | placement & memory | `schedule/memory.py`, ShapeTracker | where does the buffer actually live? |
| 08 | linearize & optimize | `codegen/late/`, `codegen/opt/` | in what order do the loops run? |
| 09 | render | `renderer/cstyle.py`, `wgsl.py` | how does a UOp become text? |
| 10 | compile & runtime | `engine/`, `device.py`, `runtime/` | what launches, and when? |

### 5.2 One example, made heavier

The narrative only works if the program is the same in every stage.

| stage | program |
| --- | --- |
| 01 | `a = Tensor.randn(4, 4)` |
| 02 | `c = (a + b).relu()` |
| 03–08 | `c.sum()` |
| 09 | the same, rendered to WGSL and to C |
| 10 | the same, launched on WebGPU — and on CPU as the oracle |

### 5.3 Lesson types

Each lesson declares exactly one type. The type decides the pane layout, nothing else.

| type | shape | example |
| --- | --- | --- |
| `line` | source highlighted, claims pinned to line ranges | `UOpMetaClass.__call__` |
| `trace` | a step scrubber over a recorded graph | a `graph_rewrite` pass |
| `concept` | prose + one figure, no code | why laziness is the boundary |
| `experiment` | editable inputs, a re-run, a diff | change the shape, watch the split |

### 5.4 Deep dives

A separate section, not filler. Each deep dive is attached to a stage and links back to it.

`uop is singleton` → 02 · `pattern matcher` → 06 · `shapetracker` → 07 · `memoryview` → 07 ·
`operator fusion` → 04 · `beam search` → 08 · `matmul trick` → 04 · `conv/arange trick` → 05 ·
`LOP3 in PTX/SASS` → 09 · `JIT explained` → 10 · `VIZ=1` → 06.

External sources are references, never copies: `tinygrad-notes` (mesozoic-egg), `Adventures with
TinyGrad` (xl0), and the 10-411 syllabus for ordering. Every external note is pinned with
`verifiedAgainst` because several describe older implementations.

## 6. The data model

Five types. If a feature cannot be expressed in them, it is not a feature.

```ts
type SourceRef = { file: string; start: number; end: number; sha: string }   // sha = hash of those exact lines
type Claim     = { ref: SourceRef; text: string; kind: 'effect' | 'reason' | 'cost' | 'trap' }
type Lesson    = { id, stage, order, kind, title, claims: Claim[], fixture?, trace?, views: ViewSpec[] }
type TraceStep = { id, stage, fn, source?: SourceRef, before: GraphRef, after: GraphRef, meta: Rec }
type Fixture   = { id, program: string, commit: string, device: string }
```

Three invariants, enforced by the build, not by review:

1. **`SourceRef.sha` must match the pinned source.** A lesson that cites `ops.py:193–196` stores the
   hash of those four lines. If upstream moves them, the build fails and names the lesson. No silent
   drift, no "the line numbers are approximately right".
2. **`manifest.declared` is derived from `claims`, never edited.** Coverage is a fold over lessons.
   A lesson that adds a claim covers lines; that is the only way to move the number.
3. **No trace, no graph.** A `trace` or `experiment` lesson without a recorded `TraceStep` id fails
   the build. The visualizer may not invent a graph.

### 6.1 The trace recorder is the product

Everything visual is a renderer over recorded traces. So the recorder is not tooling — it is the
compiler that produces the course.

```
tools/recorder/
  record.py        # runs tinygrad at the pinned commit with hooks installed
  hooks.py         # wraps UOpMetaClass.__call__, graph_rewrite, to_program, linearize
  emit.py          # writes traces/<fixture>/<step>.json + graph diffs
```

Rules that make the output teachable:

- **Deterministic.** Fixed seed, one device, `BEND_NO_TELEMETRY`-equivalent env hygiene. Two runs
  must produce byte-identical JSON — this is a gate, not a hope.
- **Diffs, not dumps.** A step stores `before`/`after` node ids and the edge delta. A 118-node dump
  per step is unusable in a browser.
- **Ids are stable across steps.** A node keeps its id through rewrites, so the visualizer can say
  "this node became that one" instead of "everything changed".
- **Every step carries a `source` ref** — the function that performed it. This is what makes the
  synchronized highlight possible.

## 7. Browser execution

Three tiers, built in this order. The first ships without the third existing.

**Tier 1 — fixtures (ships first).** The recorder's JSON is the course. Every lesson, graph, and
kernel is a file. No runtime in the browser at all. This is 80% of the teaching value and 0% of the
risk, and it means the course can launch before the playground works.

**Tier 2 — a declared subset in TypeScript.** A port of the UOp core plus WGSL emission, covering a
declared set of ops. Verified the way this repo already verifies ports: pin upstream, run both,
compare bytes across a corpus. The subset is discovered from a capability table, never a hand list,
and the UI says `37 of 75 ops` — with the 37 computed.

**Tier 3 — Pyodide, real tinygrad.** `ops_webgpu.py` exists but binds `wgpu-native` through ctypes,
so it cannot work in a browser as-is. A `js.navigator.gpu`-backed device shim is plausible and
unproven. Do not promise it; do not architect around it.

The good news, measured: `renderer/wgsl.py` is 124 lines and `runtime/ops_webgpu.py` is 222. The
WGSL path is small — the cost is the UOp pipeline above it, which is why tier 2 is a port with an
oracle and not a rewrite.

### What the playground may and may not do

- May: edit the fixture, change shapes/dtypes/ops inside the declared subset, re-run, diff.
- May not: silently fall back to CPU and claim it ran on WebGPU. The readout names the device.
- When an op is outside the subset, say so and name the missing op. A greyed control with no
  explanation is a lie about capability.

## 7.5 The voice track

Narration is recorded, not synthesised, and it drives the lesson the same way a trace drives the
graph: **from a file that was derived, not hand-timed.**

A `Timeline` is `{ lesson, mode, duration, gap?, verified, beats: [{ id, start, end }] }`.
`packages/course-voice/src/track.ts` answers `beatAt(ms)` and `positionAt(ms)`; the player asks
where it is and never computes a beat from the script. Two ways to produce one:

- **clips** — one file per beat. Boundaries exact by construction, and one sentence can be
  re-recorded without touching the rest.
- **take** — one continuous read with a 0.4 s pause between beats. `sync.py` runs `silencedetect`
  and puts each boundary at the midpoint of a pause.

The gate is the refusal. If a take has any number of internal pauses other than `beats - 1`,
`sync.py` exits **3** and says how many it heard. It does not guess: a wrong timeline looks
perfectly healthy in the player. `validate(t)` is the second gate — contiguous beats (or gaps no
larger than the declared pause), a `verified` flag, and a last beat that reaches the end.

Measured 2026-11-09: the take path recovers 5 beats from a synthetic 8 s file with boundaries at
1.30 / 2.90 / 4.50 / 6.10 and refuses a flat file with `rc=3`; `bun test` is 11 of 11. The draft
pipeline has produced real audio for 01.1 — 55.2 s, five beats, marked `draft: true`.

Drafts exist so the player is never blocked on a microphone. `draft.py` renders each beat with
macOS `say`, measures the clips, and writes the same timeline. Replacing a draft with a take is a
file replacement, not a code change. Workflow: `tools/voice/README.md`.

## 8. Repository layout

`nub` workspaces, same shape as `braven-mvp`.

```
apps/webapp                 TanStack Start + Vite, SSR, routes
packages/course-schema      Schema.Class types, decode/encode, manifest types
packages/course-engine      coverage math, progress, lesson graph, ref verification
packages/visualizer         React Flow + ELK adapters, one per stage
packages/playground         UOp subset, WGSL emit, WebGPU binding
packages/ui                 tokens, primitives, chrome — shadcn where it fits
content/stages/*.ts         ten stage declarations
content/lessons/*.mdx       prose + claims
fixtures/*.py               the running examples
traces/                     generated, committed, small
tools/recorder/             Python, runs upstream tinygrad
vendor/tinygrad/            pinned submodule or vendored tree
```

`traces/` is committed because it is the product and because CI must be able to diff it. It is also
why `record.py` has to be deterministic: a non-deterministic recorder produces a diff every night
that nobody can read.

## 9. Stack, with reasons

| choice | why | what it replaces |
| --- | --- | --- |
| **TanStack Start** | server functions for the recorder API and progress, file routes keep the 10-stage tree literal | Next.js |
| **Effect 4** | the manifest builder, ref verification, and progress are pipelines with typed failures; these are exactly the places where a silent `catch` costs you a wrong coverage number | ad-hoc async |
| **Alchemy** | deploy the app + a trace store in one declaration; already the house pattern | manual CF config |
| **shadcn/ui** | primitives without a design system fight; we reskin everything, but focus traps, popovers, and menus are solved | hand-rolled a11y |
| **CodeMirror 6** | read-only source with line decorations, gutter markers, and click-to-claim. Monaco is a whole IDE we do not want | Monaco |
| **React Flow + ELK** | the graph is a product surface, not a diagram. ELK does the layout; do not write a layout engine | d3 + dagre (tinygrad's own viz) |
| **Shiki** | highlighting that matches the static and dynamic views; TextMate grammars, no runtime cost | Prism |
| **Effect Schema** | `SourceRef`, `Claim`, `TraceStep` are decoded at the boundary and are the build's contract | Zod |
| **Fumadocs** | MDX pipeline + search only. Not the app shell — lessons are too custom | a docs theme |
| **Bun** | test runner + bundler already in use | — |

Deliberately absent: a charting library (the graphs are ours), an icon package (glyphs), a CSS
framework (tokens are 80 lines), a state manager (URL + atoms), a CMS (content is code).

## 10. What "done" means

Every milestone ships something a person can use, and every one has a gate that can go red.

**M0 — shell.** Routes, tokens, chrome, the course map. Gate: Lighthouse ≥ 95 on `/course`, zero
layout shift, keyboard-navigable.

**M1 — one lesson, end to end.** Stage 02 · lesson 02.4, `UOpMetaClass.__call__`, with real source,
claims, a hand-checked graph, and the transport. Gate: `verify:refs` passes; the lesson is
completable with the keyboard; the graph matches a recorded trace byte-for-byte.

**M2 — the recorder.** `record.py` emits traces for the 8-line fixture across 10 stages. Gate: two
runs are identical; the trace covers ≥ 90% of nodes; every step carries a source ref.

**M3 — the map is real.** All 10 stages with honest budgets, coverage computed from claims. Gate:
`verify:coverage` recomputes the census and asserts the manifest sums; a hand-edited number fails it.

**M4 — the visualizer.** One framework, ten adapters, synchronized selection. Gate: selecting a
source line highlights the right nodes in ≥ 3 stages; the before/after diff never draws a hand-made
node.

**M5 — the playground.** Tier 2 subset, WGSL, WebGPU dispatch. Gate: the subset's output is
byte-identical to pinned tinygrad across the corpus; the capability count is computed; unsupported
ops are refused by name.

## 11. Risks

| risk | severity | mitigation |
| --- | --- | --- |
| upstream drift makes half the citations wrong | high | hashed `SourceRef`; the build fails; `/pin/[commit]` keeps old versions alive |
| the recorder is non-deterministic | high | two-run byte compare in CI; ids assigned by structure, not by counter |
| tier 2 becomes an unbounded port | high | declared subset only; oracle-diffed; refused by name outside it |
| the course becomes a debugging tool | medium | every visualization answers a question the lesson asked; no unlabelled graph |
| 24 lessons × 8 claims is a lot of writing | medium | author one stage fully before opening the next; the schema is the contract |
| teaching order confuses people who wanted source order | low | `skip to the kernel` on the landing page; stage pages are individually complete |

## 12. Decisions (taken 2026-11-09)

1. **Vendor, do not submodule.** `references/tinygrad-latest` is a shallow clone at `6295132e`,
   gitignored; the course cites that tree and `tools/verify.py` hashes against it. A shallow clone
   is reproducible in one command; a submodule adds a network step to every build.
2. **Sound on by default,** with a visible toggle in the chrome, persisted, and never on hover.
3. **Two examples, not one.** Elementwise for acts I–II; matmul for act III's optimisation stage,
   where a single elementwise op cannot show a tiling decision.
4. **The playground ships first,** in fixture mode. It is the demo, and everything it needs is
   already needed by the course.
