THE DECLARATION -- four conventions, and where each side implements it
==============================================================================

ABI-1  flat frame, arity is a property of the CID
    A seam receives its arguments as a POSITIONAL frame whose length is
    cid_arity(the CID).  `f[i]` is argument i.  An H.I64 argument is ONE
    slot, not two -- it is a constructor node that the lane must OPEN.
    Arity is declared once, in dtype.bend's signature, and both lanes must
    consume exactly that many arguments.

ABI-2  a record crosses BY FIELD NAME, and the names are hi/lo
    An H.I64 crosses the JS boundary as a JS OBJECT carrying its BEND FIELD
    NAMES, {hi, lo}.  It never crosses as positional fst/snd.  There is no
    name at all on the C side: a record is a constructor node and is opened
    POSITIONALLY by ctr_take.  So `p.fst`/`p.snd` and `a[0]`/`a[1]` are BOTH
    wrong, in opposite directions, under the same one CID with the same name.
    The names are load-bearing because they are the only thing the two
    representations share.

ABI-3  pair order: the value is (hi << 32) | lo
    The two U32 words of an I64 are ordered HIGH FIRST.  hi is bits 63..32,
    lo is bits 31..0.  Both lanes, both directions.

ABI-4  scalar transport: an F32 crosses as its BIT PATTERN
    A U32 crosses as itself in both lanes.  An F32 crosses as its 32-bit
    PATTERN in C and as its VALUE under node, and each lane must undo that
    on the way in and NOT undo it on the way out.  Concretely:
      C   : the frame slot IS the pattern.  Read it with (u32)f[i].  Answer a
            pattern.  No conversion anywhere.
      node: op.args carries the VALUE (bend's JS book emits 1.5, not
            0x3FC00000) and f32_show() consumes the raw RESULT as a value, so
            the JS lane must answer a VALUE.
    So dtype.js is written in two styles at once -- fp8_decode answers a
    pattern while dtype_bf16/dtype_fp16 answer a value -- and only one of
    them is what the JS backend consumes.
