## CAN IT FAIL — THE COLUMN THE BRIEF ASKS FOR

**70 of 83 can exit non-zero. 13 cannot** — MEASURED, and this list is the measurement, not a
guess at it (a first draft of this file named `checks/fw_live.py`, `checks/reset.py`,
`checks/plant.py`, `checks/bounded-selftest.sh` and `gates/ew-consts-oracle.py`, none of which
are in it, and omitted four that are):

| the 13 that cannot fail | what it actually is |
|---|---|
| `checks/cli.py`, `checks/run.py`, `checks/serve.py`, `checks/compile.py` | tooling, not gates |
| `checks/llama.py`, `checks/sz.py` | launchers |
| `checks/coverage.py`, `checks/process_replay.py` | report writers |
| `checks/graphcmp-census-audit.py`, `checks/test_rewrite_bottom_up_gate.py`, `checks/render-gate-oracle.py`, `gates/wk-f32-rows.py`, `gates/ops-core-oracle.py` | oracles/row-generators: **supposed** to be infallible, since a lane's exit status is `Gate.run`'s business |

**So "cannot fail" is not the defect. The 70 that can and are never run are.**

## THE THING THAT MATTERS MOST IN THIS TABLE

**14 of 83 go through `gates/gatekit.py`.** `Gate.__init__` is the one place every gate would
pass through if answer 3 were true. It is not. See the report.

**WHAT THE INSTRUMENT CANNOT SEE, NAMED:** (1) a gate outside `checks/` and `gates/` — the two
homes are a list, and adding a third means editing `HOMES`; (2) any gate invoked as a
`subprocess` from a wrapper rather than run directly, which is why `checks/sb-gate.sh`'s lane
list is invisible here; (3) whether a gate is ever RUN — nothing here executes one, deliberately,
because `bend` peaks at 1,468 MB against a 2,048 MB ceiling; (4) a gate whose defect is in what it
*asserts* rather than in where it *stands* — `checks/sb-gate.sh` gates correctly on a literal
list of three lanes and this instrument cannot see that, only that its root is right.
