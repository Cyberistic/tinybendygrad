# THE RESIDUE, GROUPED BY WHY IT IS STILL HERE, WITH THE CHEAPEST TEST THAT WOULD SETTLE IT

Measured 2026-10-06 by `checks/residue.py`, liveness window **0** (see §0). `sweep` had **361** rows in
`DELETE` at the moment of measurement; seven units were writing into the tree throughout, so the totals
drift by a few rows per minute and **only the `AUTHORED` count is stable across runs — it has been 181
on every run since the authority call was added.** Where a group is a live population the count is given
as a range across runs.

## 0. THE NUMBER IS A FUNCTION OF THE CLOCK, AND OF THE CITATION CORPUS THE CLEANUP SHRINKS

Same tree, same session, four `--plan` runs:

| window | DELETE |
|---|---|
| off | **331, 343, 359, 361, 364, 367** |
| 60 min (the default) | 150, then 14, then 14, then 14 |
| 1440 min | 0 |

`--live-minutes` is not a filter on the tree; it is a filter on **when you looked**, and seven units
were writing. A number that moves 26x while nobody edits anything is not a measurement of the tree.

**So read the row counts below as a snapshot with a band, not as values.** The window-off total drifted
**331 → 367 over the twenty minutes of this analysis** purely from units adding files, and the per-group
counts inherit that. **The one figure that has not moved once is `AUTHORED` = 181**, because it is the
only group decided by a call rather than by a clock. Every `LIVE` count in this project is a statement
about the last hour, not about the residue, which is why `000-the-residue.md` is written with the window
**off** and says so in its own header.

## 1. IS THE 150 A COUNT OF JUNK, OR OF *UNREFERENCED* FILES? — **UNREFERENCED, AND THE INDEX IS WRONG**

**`checks/differ.py:156` exports `declared()` — "Every `.txt` artifact `cmd_run` writes, with its
extension, as a set of names" — and `checks/no-txt.py` already calls it for exactly this reason.**

| measurement | count |
|---|---:|
| `runs/graphcmp/D/` rows in `DELETE` | 136 |
| …of which `differ.declared()` renders | **136 (100%)** |
| `.agents/slop/spine/art-a/` rows | 47 |
| …of which `differ.declared()` renders | **47 (100%)** |
| whole residue, `AUTHORED` | **181** |
| whole residue, names visible as a LITERAL token in `checks/`+`gates/` | **1** |

`differ.py:166-172` builds them: `f"D1-graph-{g}.txt" for g in WANT`, `f"D2-canon-{s}-{g}.txt"`,
`f"D2-cmp-{g}.txt"`, and the `.err` twin beside each. **The corpus indexes literal tokens. The
project's naming authority CONSTRUCTS names.** A file whose reference is an f-string is invisible to the
reference test, and `DELETE` is measuring "referenced by no literal" while being published as "junk".

**The residue is a count of files unreferenced by the INSTRUMENT. It is not a count of junk.** Only one
number in this directory settles the difference, and it is not a judgement: *ask the generator.*

And the trap the brief names is real and measured: the earlier pass that deleted 110 byte-identical
copies shrank `mentioned_filenames`, which **demoted** files and moved the DELETE bucket 151 → 150.
Repointing a copy into its authoritative home makes the tree honest and makes the KEEP set smaller at
the same time. **A cleanup that improves its own instrument's number is not a cleanup, it is a
self-defining one.** So the DELETE bucket is not a stable measure of the tree's critters; it is a
function of a corpus the cleanup itself edits. That is why the verdict below is per-row and testable,
and why the headline is a count of *groups*, not of files.

### The three groups that need a person, and the one measurement that would shrink each

**G8, 41 rows, is the largest open group and it is not a judgement call — it is a missing
discriminator.** These rows are named only by other residue files: by `spine/SPINE.md`,
`_cite/cites.json`, `difftxt/DECISION.md`, `stalefix/REPORT.md`, `graphrestore/RESTORE.md`,
`boundedfix/repro.py`, `abi4/README.md`, `clearfix/REPRO.rows`, `opsbend-milestone.sh`,
`slopcopies/MANIFEST.md`, `ishr/REPORT.md`, `e2e_mm_run.mjs`, `_cite/cite.py`,
`clearfix/clearfix-repro.py`, `fixures/reconcile-dangling.py`, `txtgen/orphan-plant.py`,
`graphrestore/portside.py` and others. **They are UNKNOWN, not CITED and not DELETE**, because a
citation from inside the tree being swept is either a real dependency between two of the residue's own
tools or a shadow tree naming the files it copied, **and those two are not distinguishable from where I
sit.**

The deciding test, and it is cheap: **a residue-internal citer that is itself a COPY is a shadow tree, and
one that is not is a real dependency.** `checks/residue.py` already computes sha256 over the whole repo
for G3, so the discriminator is one dict lookup per row against the twin map it already has. If the
citer has no twin outside the residue, the citation is real and the row is CITED. **That is the single
highest-value thing left to do to this instrument, and it converts 41 UNKNOWNs into decided rows.**
`_cite/cites.json` is already known to be a scan record rather than a citer —
`slopcopies/CITATIONS.tsv` says so in its own `reason` column, *"generated by
`.agents/slop/_cite/cite.py:135`; also a BASENAME-keyed index, which is trap 1"* — which is what
`MANIFEST.tsv`'s `SKIP` rows already model.

**G9, 29 rows: the extension test.** `orphan.rows` (an output) and `graphcmp.py` (a tool) can sit in the
same directory with the same missing report. The first is junk; the second is a question about a person.
`sweep` cannot tell them apart. `checks/residue.py` can, from the extension alone, and that is what
turned 65 `UNNAMED` into 39 `UNNAMED` + 29 `UNKNOWN`. The flag is mechanical; the decision is not.

**G7, 19 rows: the house rules.** `strays/` 4, `strays-root/` 1, `runs/portexec/` 3, plus 11 more.
**They are counted, not hidden** — a group excluded from the walk is a group hidden rather than
analysed, which is the `LIVE_UNITS` shape one level up. Note `runs/portexec/` is unprotected only because
`sweep.PROTECTED` is anchored `^\.agents/slop/(e2e|e2e_port|f64|portexec)/`: **the same directory name is
protected under one root and deletable under the other.** One regex, three files.

## 3. `LIVE_UNITS` IS THE SAME FAILURE, STILL UNFIXED, AND I AM THE ONE WHO CANNOT FIX IT

The header already diagnosed it: *"six finished units, 2,353 files, 53% of the tree, every one named by
0 files outside themselves… **A LIST THAT OUTLIVES ITS UNITS IS NOT A SECOND BELT, IT IS THE ONLY
BELT**"* and *"**THE MTIME WINDOW IS THE LIVENESS GUARD, EXACTLY AS THE COMMENT ABOVE SAYS**."* The comment
concludes the list is redundant. **The list is still there.** `LIVE-UNIT` currently covers **342 files,
28% of the residue**, off a 14-name tuple inside a Python file.

**MEASURED, and it corrects the obvious recommendation: `LIVE_UNITS` CANNOT simply be deleted.** Of its
342 files, **109 are ALSO inside the 60-minute mtime window** and 233 are not. So for those 109 the list
is redundant today, and for the other 233 **the mtime window does not reach them at all** — which is
precisely the case the list exists for. Deleting the tuple without shipping per-directory aggregation in
the same change would expose 233 files. **The two have to move together, and the header's own conclusion
is only right if the aggregation lands first.** Per-directory aggregation is 6 lines in
`checks/residue.py` (`dir_ages`) and needs no roster, so it cannot go stale the way the tuple did.

Three further consequences, all measured:

- **The tuple is the roster and the roster is nowhere else.** The house rules say 21 units are running;
  `sweep.LIVE_UNITS` names 14; `git grep` finds no other roster. A third party cannot exclude the live
  units from a walk, because the live units are not written down anywhere a third party can read.
- **`spine/` and `clearfix/` and `fixures/` and `txtgen/` and `boundedfix/` are LIVE RIGHT NOW and are not
  in the tuple.** At the 60-minute window they are protected only because a unit happened to write in the
  last hour — G2 above, 144 rows. **The next unit dispatched after this measurement will put its whole
  directory into DELETE, and the mtime window will not save the files it has not written yet.** That is
  the fourth instance, and it is the one the comment predicts.
- **`LIVE` is checked AFTER `LIVE-UNIT` in `main()`, so for those 109 files the list is what is holding
  them, not the window** — the guard `v not in ("PROTECTED", "LIVE-UNIT")` stops the window from
  relabelling them. The redundancy is invisible from the plan's output, which is why it survived.

## 4. WHAT I COULD NOT SETTLE

- **G8's 41 rows.** Decided above how, not done. The discriminator is not implemented.
- **Whether G6's 39 `UNNAMED` rows are junk.** Nothing measured says they are, and nothing measured says
  they are not. At the 60-minute window **the `UNNAMED` count is 0** — every one of them sits in a
  directory a unit wrote inside the hour — which is the strongest single argument that the 150 was never
  a count of junk. It is also the argument that the honest answer is "ask the unit", which is not a test.
- **The four belt disagreements (G10).** `git grep -w -F` and a `str.translate` table disagree on four
  basenames and I did not chase which is right. They are listed in `002-unknown.md`.
- **Whether `spine/art-a/` should exist at all.** Its files are byte-identical to `runs/graphcmp/D`
  files, so G3 says COPY — but a snapshot taken *before* a change is the only record of the "before".
  **G3's rule is wrong for a deliberately-taken snapshot**, and I could not tell from here whether
  `SPINE.md` says the snapshot is the point. 7 residue rows are named by `spine/SPINE.md`, so somebody
  thought about it. This is a hole in G3 and it is not fixed.
- **The 21-vs-14 live units.** I excluded `sweep.LIVE_UNITS` because it is the only roster that exists,
  and said so rather than inventing the other seven.
- **Whether the 6 dirty `NAMED_BY` files changed any verdict.** `committed_named_text()` reads
  `git show HEAD:`, and 6 of the 174 tracked corpus files are modified in the worktree — so a report that
  has been edited but not committed contributes its OLD text. **`.agents/TODO.md` at HEAD mentions
  `stage-verdicts.py` 0 times; the worktree mentions it once.** The error is bounded at 6/174 files and I
  did not quantify its effect on the counts.
