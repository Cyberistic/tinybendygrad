## 3. THE TEMPLATE CHECK -- what name-and-arity cannot do

Name-and-arity proves the counterpart def EXISTS and its signature
AGREES.  It cannot see WHICH FUNCTION a body calls, so a body calling the
wrong getter at the right arity passes it.  The stronger check is a
TEMPLATE check: these bodies are generated, so they must match the shape
autogen.py:240-241 emits.

  THE TEMPLATE, lifted verbatim from autogen.py:240-241:
    @dll.bind(<ret>, <arg types>)
    def <name>(<anm>:<hint>, ...) -> <ret>: ...

  @dll.bind lines in corpus                : 4864
  ...immediately followed by the def line  : 4864
  RATIO shaped/all                         : 4864/4864

  => ONE TEMPLATE COVERS EVERY BOUND BODY.  A per-def gate would be 4,864
     copies of this one shape.  The template check is strictly STRONGER
     than name-and-arity because it also pins the RETURN TYPE, the
     PARAMETER NAMES, the PARAMETER ANNOTATIONS and the `...` body,
     none of which a name+arity diff looks at.

## 4. WHAT THE TEMPLATE CANNOT SEE (stated, not hidden)
  The template pins the SHAPE of the emitted def.  It cannot see:
    - whether the ctypes TYPE SPELLING tname derived is correct
      (`c.POINTER[struct_Pair]` vs `ctypes.c_void_p`) -- that is WALL 4,
      the unported record arm, reproduced at .agents/slop/ag-wall4-repro.bend;
    - whether the FIELD ORDER inside a struct is right -- the template
      never sees struct bodies;
    - whether register_fields OFFSETS are right.
  So a template check covers the FUNCTION TRAMPOLINES and none of the
  STRUCT LAYOUTS.  Reported, not papered over.
