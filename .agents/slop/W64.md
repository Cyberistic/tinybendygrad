# W64 — `Nat`'s real range, and one `f64` add

Unit: `.agents/slop/w64/`. Nothing committed. Compiler: **Bend 2.0.34** via
`./bin/bend` (the `2.0.35 is available` line is an upgrade nag and every wall
below is measured on the 2.0.34 that actually runs here).

Reproduce, in order:

```sh
./.agents/slop/w64/gen.sh      # W-1/W-2, Nat ceiling: ladder + controls
python3 .agents/slop/w64/gen_w3.py    # W-3, Word(64n) 64-bit integer add + gate
python3 .agents/slop/w64/gen_w4f.py   # W-4, the f64 add, against CPython
```

Each generator prints its own gate rows and exits non-zero on any failure.

## W-1 / W-2 — `Nat`'s measured range

`nat_walk.bend` doubles from the literal ceiling `4294967295n`, printing before
each doubling. The order is self-checking: the fuel column descends by exactly 1
per line and the value column doubles, so a fold/reversal bug could not hide.

```
W-1 fuel=39 val=4294967295        W-1 fuel=30 val=2199023255040
W-1 fuel=38 val=8589934590        W-1 fuel=29 val=4398046510080
W-1 fuel=37 val=17179869180       ...
W-1 fuel=23 val=281474976645120   <- last line printed
bend: a Nat past the largest immediate 2^48-1
```

Then `gen.sh` pins the boundary exactly, one candidate per process so a failure
cannot hide later rows (`nat_walk.bend` + ladder, with **both** controls armed):

| candidate | value | outcome |
|---|---|---|
| 2^48 − 2^16 | 281474976645120 | SURVIVED |
| 2^48 − 2 | 281474976710654 | SURVIVED |
| **2^48 − 1** | **281474976710655** | **SURVIVED — largest that survives** |
| 2^48 | 281474976710656 | **DIED** |
| 2^47 − 1 (odd) | 140737488355327 | SURVIVED |
| 2^47 + 1 (odd) | 140737488355329 | SURVIVED |
| 2^47 + 2 | 140737488355330 | SURVIVED |

Exact error at the first failure:

```
bend: a Nat past the largest immediate 2^48-1
```

Controls: `must-survive exit=0`, `must-die exit=1`. Both armed, so neither the
ladder nor the compiler is disarmed.

**Three findings, and one of them kills an inherited claim.**

1. **`Nat` max = 2^48 − 1.** Runtime range `[0, 2^48−1]`. The literal cap is
   2^32 − 1, so runtime and literal differ, as observed.
2. **The bound is MAGNITUDE, not parity.** 2^47 + 1 is odd and survives. Had I
   stopped at the doubling ladder I would have had no way to tell a magnitude
   ceiling from an even/odd one; the parity ladder is the row that decides it.
3. **The inherited claim is wrong by 8 binary orders.** It said *"works to 2^51−1
   and aborts at 2^52−1, while its own error message says 2^48−1"*. Measured:
   the ceiling is 2^48−1 and **the error message is exactly right**. Do not
   repeat the 2^51 figure.

**A trap worth keeping.** My first ladder was built on `base = 2^48 − 2^16`
written down as `2^48`. It produced *"2^48 printed and 2^49 died"* — a ceiling
**above** the error message's own bound, i.e. a self-contradiction. That
contradiction was the tell that my hand arithmetic, not the compiler, was wrong.
A measured result that contradicts the tool's own error text should be treated as
a suspect result until the arithmetic is re-derived.

## Is `Nat` a safe `U64`? Is it a safe `I64`?

**`U64`: no.** 48 bits of magnitude against 64 required. A `Nat` can carry a
`U64` **only when that value is below 2^48** — so the FFI handle route already
in this project works for addresses that happen to be small, and silently breaks
on the upper 16 bits. It is not a `U64`; it is a 48-bit word wearing a `U64`'s
name.

**`I64`: no, and much further from yes.** `Nat` is a Peano numeral —
`type Nat is Data: Zero{} | Succ{pred: Nat}` — so there is **no sign at all**.
`Nat.sub(0n, b)` returns `0n`; it saturates, it does not go negative. Every
negative `I64` is unrepresentable, and `I64` needs 63 magnitude bits where `Nat`
has 48.

**The f64 consequence, which is the whole reason this matters:** a 64-bit bit
pattern fits a `Nat` only in the bottom 48 bits. CPython-computed, **99.998474 %
of all 2^64 f64 bit patterns cannot be carried in a `Nat`**. So the
"f32 crosses the FFI as a `Nat` bit pattern" route already verified here **does
not generalise from f32 to f64** — an f32 pattern is 32 bits and always fits; an
f64 pattern is 64 and almost never does.

## W-3 — the 64-bit container exists (and it is not the wall)

`bend base --types` lists 103 lines and the entire numeric surface is `Nat`,
`U32`, `F32`: **no `F64`, no `I64`, no `U64`**, widest word `Word(32n)`. That
reads like a wall. It is not.

`Word(p)` is `Word.Con{head: Bool, tail: Word(p)}` and `Word.shl` puts the
incoming bit at the **head**, so a `Word(n)` is an **LSB-first bit list**. Base
ships `Word.add/sub/mul/inc/adc/shl/shr/cmp/and/or/xor/not/to_nat`. Measured, via
`w3_wordadd.bend`:

```
A = 0x0123456789abcdee   B = 0x1111111111111110
Word.add(64n, A, B)      = 0x123456789abcdefe     (CPython: AGREE)
```

Gate: 5/5 PASS, including "sum is **not** the MSB-first rendering" so a transposed
readback convention cannot pass, plus an independent decode of bend's own output
back to an integer (`0x123456789abcdefe`) so the encoder cannot be wrong in the
same direction as the comparator. A control Word built from the literal pattern of
1 reads back as `1`.

So: `type F64 is Data: F64{data: Word(64n)}` **typechecks as a user declaration**,
and 64-bit integer arithmetic on it is correct.

One sharp edge: `Word.to_nat(64n, w)` **dies** with the same 2^48−1 message. A
`Word(64n)` cannot be read out through `Nat`. Reading it must stay in the bit
list, or cross the FFI.

## W-4 — ONE `f64` add. It works, bit for bit.

The asked-for case, `1.5 + 2.25`, against CPython's `struct.pack('<d', …)`:

```
1.5  = 0x3FF8000000000000
2.25 = 0x4002000000000000
1.5 + 2.25 = 3.75 = 0x400E000000000000    <- hi=0x400E0000 (1074659328), lo=0
```

`w4_f64add.bend` + `f4_add.c` produce exactly that, and two more rows:

| row | fixture | bend hi/lo | CPython | |
|---|---|---|---|---|
| 0 | 1.5 + 2.25 | 1074659328 / 0 | 0x400E0000 / 0 | PASS |
| 1 | 1.0 + 0.5 | 1073217536 / 0 | 0x3FF80000 / 0 | PASS |
| 2 | 0.0 + 0.0 | 0 / 0 | 0 / 0 | PASS |

Row 1 is a **plant** (a different sum must move the answer) and row 2 is a
**disarm** (a constant-returning harness passes row 0 and fails both). All three
are required; row 0 alone cannot fail a constant.

**So the port is not blocked on f64 arithmetic.** Two `U32` halves per operand
cross the boundary, the `double` is reassembled inside C and written back out as
two halves, and **`no `double` type ever crosses the FFI`.** Consequences:

- The 17 libclang bindings blocked on `int64`/`uint64`/`double` are blocked on
  **the libclang binding signatures**, not on Bend's ability to move 64 bits or
  to compute in f64. Any binding whose C side is re-expressible over `u32` pairs
  is unblocked.
- Overflow/underflow are C's, not mine: the add is `x + y` on `double`, so
  IEEE-754 rounding, inf, nan and subnormals are whatever the host FPU says. That
  is a *portability* caveat, not a blocker, and it is bit-identical to CPython on
  this machine.
- `H.I64` in the port is already `I64{hi: U32, lo: U32}`
  (`tinybendygrad/helpers.bend:1648`) — the same two-half shape that works here.

## The measured foreign-def shape (four rules, each learned by a failure)

None of this is in the guide, and each rule cost a compile round:

1. **A `def` carrying a `.c` import must be UNTYPED.** Types go on a separate
   `law` of the same name. A typed `def … -> IO(U32)` with a `.c` import is
   rejected: `Error: a foreign def without a .js import: f64_add`.
2. **`import` is not admissible inside a `law`** — `expected : 'def', 'type' or
   'law' / observed : 'i'`. A law is a proved total function.
3. **A foreign def cannot be run by `bend <file>`.** It needs
   `bend <file> -o out.c` then `cc out.c -o out`. `bend <file>` alone reports
   `SOME PROOFS FAIL` / `no effect registers …` / `without a .js import`.
4. **A `.js` effect source registers itself**: `io_eff(CID(name), name_run, need)`.
   `export` is a syntax error — it is a plain script, not an ES module.

## Does `dtype.bend`'s 14 need types, or `math.*`?

**Neither. The premise is wrong on both counts, and this redirects the build
order.**

**Types are already there.** `tinybendygrad/helpers.bend:1648`:

```
type I64 is Data:
  I64{hi: U32, lo: U32}
```

**The implementations are already there.** `tinybendygrad/runtime/dtype.c` is
11,828 bytes with the fp8 bias/sig/mant/denorm/ovf/min/max tables and
`fp8_encode`; `tinybendygrad/runtime/dtype.js` is 6,200 bytes and registers all
eleven effects at `dtype.js:160-171`:

```
io_eff(CID(Dt.bf16), dtype_bf16);          io_eff(CID(Dt.i64_trunc), …);
io_eff(CID(Dt.fp16), dtype_fp16);          io_eff(CID(Dt.i64_floor_div), …);
io_eff(CID(Dt.fp8_from), dtype_fp8_from);  io_eff(CID(Dt.i64_floor_mod), …);
io_eff(CID(Dt.fp8_to),  dtype_fp8_to);     io_eff(CID(Dt.i64_cdiv/cmod/ceildiv), …);
```

**The 14 are split 6 / 8 and neither half is a math problem:**

- **6 `Dt.i64_*`** (`i64_trunc`, `i64_floor_div`, `i64_floor_mod`, `i64_cdiv`,
  `i64_cmod`, `i64_ceildiv`) — blocked on **`H.I64`, which exists**. They are
  64-bit floor/cell division on the `hi`/`lo` pair; `dtype.js` already computes
  them via `floor_pair`.
- **8 `Dt.bf16`, `Dt.fp16`, `Dt.fp8_from`, `Dt.fp8_to`** plus the four Bend
  wrappers `float_to_bf16`, `float_to_fp16`, `float_to_fp8`, `fp8_to_float` —
  pure integer **bit manipulation** on `U32`/`F32`, which exist. bf16→f32 is a
  16-bit left shift. fp8↔f32 is exponent rebias and mantissa placement.

**Why they read as red.** `--check-only` prints `SOME PROOFS FAIL / Error: 14
defs rely on unsafe or foreign code` and names them. That is the **definition of
an FFI seam**, not a defect: a foreign def is outside Bend's proof system by
construction. The 10 Bend `laws` above have no body because they are foreign —
the same reason `ops_webgpu` and six other files are green *because* they declare
no foreign effect. **So these 14 are not a porting backlog; they are the seam
being a seam, and the count should not be read as 14 missing features.**

**And the `math.*` concentration does not exist.** Against the frozen census
(`wallmap/census.json`, 1028 rows): **10 rows** mention `math.<fn>`, across **2
port files**, naming **3 functions** — `math.log` (5), `math.pi` (4),
`math.sqrt` (2). The brief's "~35 targets wait on one absent `math.*` library" is
not supported. Inspecting those rows, `math.pi/2`, `1/math.log(2)` and
`math.sqrt(2/math.pi)` appear as descriptions of **F32 literals** — constants
tinygrad folds in Python (`elementwise.bend:42-43`, `:746-760`). `math.gcd` is
already implemented in integer arithmetic (`helpers.bend:2074`). The remaining 62
`math.` mentions tree-wide are in comments, transcendental decomposition, and
renderer backends.

**So there is no missing math library to build. What is missing is F32 literal
constants and F32 arithmetic** — and that is the build to do first, not a math
module.

**CORROBORATION, and it cuts against my own figure.** HEAD is
`199b2feb3 slop(mathlib): math.* DOES NOT EXIST. There is no call site. Writing it
would unblock ZERO targets -- and the name came from a TUTORIAL FILENAME.` My
census count (10 rows, and every one of them a *comment* describing an F32
literal) is consistent with theirs and strictly weaker: they measured **zero call
sites**, I measured ten comment rows and did not check whether any is a call. Per
the rule that a sibling port's wall is gated rather than reconciled, both are
recorded: their stronger claim stands, and my count should be read as an upper
bound on mentions, not on blockers.

## What this changes for the port

1. **`Nat` is a 48-bit unsigned word, not a `U64` and not an `I64`.** Any claim
   that it substitutes for a 64-bit type is true only below 2^48. The brief's
   "verified as a working `U64` substitute for a handle" holds for the handles
   actually measured and should be re-stated with the bound attached.
2. **f64 is not blocked.** Bit-exact `1.5 + 2.25` measured, with plant and
   disarm. The next execution step (`cstyle-live`'s dtype-sensitive fixture) is
   reachable over a two-`U32` boundary.
3. **The three "one fact" blockages are three different facts.** The `Nat` range,
   the 17 libclang signatures, and the f64 fixture are not one problem. Only the
   middle one is a real signature problem, and its fix is re-expressing libclang
   signatures over `u32` pairs.
4. **`dtype.bend`'s 14 are not a backlog**, and `math.*` is not a missing
   library. The highest-value next build is F32 arithmetic and literal constants.
5. **The f32→f64 generalisation of the `Nat`-bit-pattern route is invalid.**
   99.998474 % of f64 patterns do not fit a `Nat`; the two-`U32` route does.
