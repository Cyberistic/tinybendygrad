THE FIXTURE THAT ACTUALLY EXPOSES `%g`, MEASURED

  `%g` is SIX significant digits, so it is not a different shortest form -- it is a
  LOSSY one, and the fixture that shows it is NOT a lane/oracle disagreement:

      1.0000001  ->  `1`
      1.0000002  ->  `1`        THREE DISTINCT f32 values, ONE spelling.
      1.0000003  ->  `1`

  `repr` gives `1.0000001`, `1.0000002`, `1.0000003` -- three.  `canon` gives
  `f32:3f800001`, `f32:3f800002`, `f32:3f800003` -- three.

  **SO THE ROW THAT EXPOSES `dc-oracle.py:131` IS TWO DIFFERENT VALUES INSIDE ONE
  SIDE.**  No gate in this tree has a row of that shape, and `cstyle-numbers.py:5`
  states the reason in prose ("a decimal print rounds, and two rounded strings can
  agree") without ever making it a row.

THE FIXTURE THAT EXPOSES `repr` WITH NO ROUND TRIP, MEASURED

  One f32, two spellings, one value:  `F32.show` prints `1.0996094` and CPython's
  `repr` prints `1.099609375`, and both are `f32:3f8cc000`.  That is `fp16_1p1`.

  And the general form, measured through the REAL emitted `f32_show`, not a
  re-spelling of it (`references/bend/bend2/bend.ts:1197`):

      pattern 1048573611   `F32.show` -> `0.2499644`
                            `repr`     -> `0.2499644011259079`
                            `%g`       -> `0.249964`

  Three spellings, one f32.  So `mm-walk-gate.py`'s `bnd` (`repr`) would print
  `F0.2499644011259079` where `fold.bend:3165`'s `bnd_show` prints `F` ++
  `F32.show(v)` = `F0.2499644`, and the gate would report a disagreement on a
  bit-identical value.  **IT DOES NOT, ONLY BECAUSE NO ROW OF ITSS IS NON-INTEGRAL
  BEYOND `1.5`.**

WHAT I ADDED, AND WHERE

  norm/gate_norm.bend + gate_norm.py -- the four motivating cases, on BOTH lanes:
      f16_1p1     `1.1` in f16, the shortest-form trap
      f32_1p0     `1.0`, the `F32.show` -> `1` trap
      f64_2m40    `1.0 + 2**-40`, the width trap
      nan_p0/p1/neg + fp8to_nan  two NaNs differing only in payload
      bf16_1p5    a bits row on a seam that takes a PATTERN
    Every row prints BOTH `F32.show` and `U32.show(F32.bits(...))`, so the gate
    never has to choose a normaliser in order to read a value.

  norm/canon.selftest.py -- the four rows alone, plus the property the helper rests
    on, plus the PLANTS, so each row is shown able to fail:
      `repr(float(s))` is wrong on 2 of the 5 lane/oracle rows
      `f"{v:g}"`       is wrong on 0 of them and wrong on the 1-ULP collision
    A row that no instrument can get wrong is not a row, and BOTH normalisers are
    now shown getting a row wrong by name.

  norm/lint_demo.sh -- the lint's own two branches, measured: green on the tree,
    red on one planted site.  A lint pinned to a constant is the fifth instance of
    the family it exists to stop.

WHAT I DID NOT ADD, AND WHY

  I did not add `C(1.0000001)` / `C(1.0000002)` to `dc-oracle.py`, nor
  `F0.2499644011259079` to `mm-walk-gate.py` / `mm-lift-gate.py` / `mm-dt-gate.py`.
  Each is a three-line fixture and each file belongs to another unit.  Adding a row
  to someone else's gate is how two units end up editing one file, and
  `agent-core.md` is explicit that a read-only file's bug is REPORTED.  The rows are
  written out above so the owning unit can paste them.

  I DID change `jslane2/gen_f32_seam.py`, because the brief names it and because its
  fixture -- added by the JFP- unit -- HAD NEVER RUN: `dtype.bend` made `Dt.bf16`,
  `Dt.fp16` and `Dt.fp8_to` PURE, so the file's `v : F32 <- D.Dt.bf16(...)` stopped
  compiling and the whole gate printed `bend failed` and exited 1.  A fixture in a
  gate that cannot compile is not a fixture.  It now runs 7/7 on both lanes.
