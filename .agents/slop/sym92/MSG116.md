`(y + x) + x -> y + x*2` carries `fits(a, 2*x.vmin) and fits(a, 2*x.vmax)`: the doubled operand must
stay in the sum's dtype at both ends of its range. The port minted `y + x*2` unconditionally.

BEFORE / AFTER, MEASURED on int8, one arena per case, `.agents/slop/sym92/probe-263.bend`:

    narrow  x in [0,10]        -> (add y (mul x (cast:i8 c2)))   FIRES
    wide    x in [-128,127]    -> (add (add y x) x)              REFUSED

The `wide` row scales to -256/254, which int8 cannot hold.

**THIS GUARD COULD NOT BE TESTED UNTIL `sy_trunc` WAS WIDENED** (`0d89d16e`). While the rule was dead
the probe read "unchanged" for BOTH cases, and "unchanged" is exactly what a correct guard looks
like -- so an earlier attempt at this guard was reverted on evidence that could not distinguish
"refused" from "never ran". **A GUARD CANNOT BE VERIFIED ON A DEAD RULE, AND A DEAD RULE LOOKS LIKE
A CAREFUL ONE.** The order was: revive the body, then measure the pair, then land the guard.

The bounds conversion is the one `:485` already uses (`BndInt{neg, mag}` -> `i64_neg`, table from
`F.mm.sweep`) and it converts nothing else: an infinite or floating bound fails `fits` for a signed
int dtype, which is what CPython's `min <= v <= max` says.
