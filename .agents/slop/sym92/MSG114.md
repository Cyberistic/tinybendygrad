`sy_trunc` had SIX arms where `truncate` has FIFTEEN, and every narrow-int rule was dead

ROOT CAUSE OF `:263`, and it is not a `:263` bug.

`tinygrad/dtype.py:293` is the truncation table, and `DType.const` (`:83`) indexes it for EVERY int
dtype:

    if self in dtypes.ints: return truncate[self](int(val))

    truncate = {bool: bool, float16: ..., bfloat16: ..., **fp8s,
      **{n: ctypes.c_<n>(x).value for n in (float, double,
         int8, int16, int32, int64, uint8, uint16, uint32, uint64)}}

The port's `sy_trunc` had six arms -- bool, weakint, weakfloat, i32, u32, f32 -- and answered
`None` for EVERY other dtype. `mint_const_like`, `trunc_m` and `exec_alu.trunc` all read `None` as
"no answer", so every rule that builds a constant at a narrow int dtype was DEAD ON ARRIVAL.

`:263` (`(y+x)+x -> y + x*2`) was the one that got caught, and only because a probe asked its `pat`
and its `mk` separately:

    sym_251.pat(node)  True
    sym_251(node)      norewrite        <- mint_const_like answered None

VERIFIED AGAINST CPYTHON, both the shape and the wrap:

    x8.const_like(2)    CPython  CAST(CONST 2, i8)        port  (cast:i8 c2)     AGREE
    UOp.const(200, i8)  CPython  CAST(CONST -56, i8)      truncate[int8](200) = -56
    :263 now fires      port  (add y (mul x (cast:i8 c2)))

The six added arms wrap rather than truncate-toward-zero: `lo32` keeps the low word, a mask keeps the
low N bits, and a signed width subtracts 2**N when the sign bit is set -- which is what
`ctypes.c_int8(200).value` does and is the reason 200 becomes -56 and not 200.

**THE DEFECT CLASS IS THE POINT: A PARTIAL TABLE READS AS A REFUSAL, NOT AS AN ERROR.** A missing
`truncate` entry in CPython would be a `KeyError`; in this port it is `None{}`, which every caller
treats as "this rule does not apply". So the rule declines politely, the census calls the row
PORTED, and nothing is red. **`None{}` IS NOT A SAFE DEFAULT WHEN IT MEANS "NO", BECAUSE "NO" IS
INDISTINGUISHABLE FROM "NOT APPLICABLE".**
