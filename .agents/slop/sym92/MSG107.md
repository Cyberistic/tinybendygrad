`:171`'s `fits` guard, VERIFIED by before/after, and the pin rule measured

`symbolic.py:171` is SIX rows (`GroupOp.Associative`) and one body:

    fits(x, exec_alu(f.op, dtypes.weakint, [c1.vmin, c2.vmin]))

Two-stage folding replaces `(x op c1) op c2` with `x op (c1 op c2)` and computes the combined
constant in WEAKINT, so when it does not fit `x`'s dtype the rewrite changes the answer.

BEFORE / AFTER, MEASURED on int8 (`[-128, 127]`), one arena per case:

    WITHOUT the guard   (x+1)+127 -> (add x (add c1 c127))      folded to 128, impossible in int8
    WITH    the guard   (x+1)+127 -> (add (add x c1) c127)      UNCHANGED, as CPython
    WITH    the guard   (x+1)+2   -> (add x (add c1 c2))        still folds, 3 fits

The last line is what keeps the guard from being a "stop firing" hack: it refuses the overflow and
keeps the fold.

**THE PROBE HAD TO BE REBUILT TWICE AND THE REASON IS THE SAME BOTH TIMES.** Two cases sharing one
arena chain made the second case render a constant from the FIRST (`(mul c100 c2)` for a graph built
from `100`); one arena per case fixed it, and `probe-171-ops.bend` prints `root/src0/src1` op names so
the graph is checked before the answer is read. **A RENDER IS NOT A MEASUREMENT UNTIL THE GRAPH IT
RENDERS IS THE GRAPH YOU BUILT.**

AND THE PIN RULE, MEASURED rather than guessed -- `gates/symrules-census.py:99`:

    def blob_id(path):  """The git blob id of `path` as HEAD holds it, ..."""
      subprocess.run(["git", "rev-parse", "HEAD:" + rel], ...)

**THE PIN IS `HEAD:`, NOT THE WORKING TREE.** So the rows can only ever name a committed blob, and the
order is fixed:

    1. commit the `.bend`
    2. regenerate the rows           <- they now pin the commit from step 1
    3. commit the rows

Every stale pin in this session (three of them) came from doing 2 before 1 and reading the result as
"the pin is right, the gate is wrong". The gate was right every time.
