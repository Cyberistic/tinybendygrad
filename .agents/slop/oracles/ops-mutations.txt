WHAT IS NOT A BLIND SPOT, AND WAS THE OBVIOUS CANDIDATE

  `AxisType.value` is a prime candidate for a blind spot -- if no fixture had a WARP or a
  PLACEHOLDER axis, a wrong value there would move nothing. It is NOT one, because
  `axv_<NAME>` is ONE ROW PER MEMBER rather than one row per fixture, and PLACEHOLDER is
  in no RANGE fixture tinygrad builds. M2 (`PLACEHOLDER 8 -> 9`) moves `axv_PLACEHOLDER`
  and M4 (`WARP 4 -> 3`) moves `axv_WARP`. The per-member table is the whole difference
  and it costs nothing: a member with no fixture is exactly the member a fixture-driven
  gate forgets.

  The same reasoning, one level down, is why `eq_axis` is gated as TWO COUNTS and not as
  the 8x8 = 64 table. A permuted value table -- which is upstream's own defect -- leaves
  every `eqax_A_B` answer unchanged, so the table is a change detector; M22/M23 show the
  counts move on the collision's twin instead. Between `axv_*` (the permutation) and
  `eqax_collide` (the collision) both facts are covered, in 10 rows instead of 64.
