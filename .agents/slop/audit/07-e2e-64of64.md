# 07 — "E2E PASS, 64/64 u32 words"

**VERDICT: CAN-FAIL — cleanly, with two independent plants and a negative
control. This is the best-instrumented number in the set and it deserves to be
said so.**

## Subject and instrument

- **Subject:** the GPU's 64 `u32` output words of a real `(A@B)@C` matmul,
  compared bit-for-bit against CPython's 64, executed on a real WebGPU adapter in
  headless Chrome.
- **Instrument:** `sh .agents/slop/e2e.sh`, five stages, one command, `rc=0` on
  PASS. Full live run:

```
mm_e2e_in_bits_equal=True
mm_e2e_out_bits_equal=True
mm_e2e_out_words=64
mm_e2e_walk_completed=True
mm_e2e_failed=0
PASS
# 0 failed of 46 rows read          <- stage 5, the port's own ops_bend runtime
PASS
PASS (stages 1-4 and stage 5)
E2E rc=0
```

`mm_e2e_out_bits_equal` is `res["out_u32"] == o["answer_u32"]` —
**equality, not a tolerance**, on all 64 words at once.

## Plant 1 — one bit of one of the 64 words: **RED**

`e2e_mm_gate.py` reads its oracle from a module-level path
(`ORACLE = ROOT / "runs/e2e/e2e-mm-oracle.json"`, line 44), so the copy is
pointed at explicitly. Flipping `answer_u32[0]` by 1 — verified: `1 of 64` words
differ, `1044381696 → 1044381697`:

```
BASELINE                 mm_e2e_out_bits_equal=True  out_words=64  walk_completed=True  failed=0
PLANT oracle word0 +1    mm_e2e_out_bits_equal=False out_words=64  walk_completed=True  failed=1
```

**CAN-FAIL.** A single bit in a single word out of 64 turns the gate red and
counts exactly one failure. This is a bit-exact check and it is bit-exact.

## Plant 2 — the walk dies: **RED**, and nothing reads a crash as a pass

```python
res = g.get("result") or {}          # an absent result is an EMPTY result
row("mm_e2e_walk_completed", res.get("ok"), True)
```

```
PLANT gpu walk died       mm_e2e_out_bits_equal=False out_words=0  walk_completed=False failed=20
```

The file's own comment records why: an earlier version raised
`"operands could not be broadcast"` on the absent readback, so **the harness saw
zero `# FAILED` lines and read a crash as a pass.** That is this brief's headline
defect, found and fixed inside the project already — and the fix is load-bearing
in the right way: `mm_e2e_walk_completed` is the row that says so in one place,
and my plant moves it.

## A harness lesson worth recording

My first attempt at Plant 1 did not move the number. The reason was mine, not the
gate's: I planted a copy of `e2e-mm-oracle.json` into `$TMPDIR` and ran
`e2e_mm_gate.py <copy>/e2e-mm-bend.txt` — and the gate **ignored the copy's
oracle** and read the live one, because `ORACLE` is a module global, not a
relative path. The number stayed green for a reason that had nothing to do with
the gate's correctness.

That is the fourth time in this audit that a plant failed to land for a reason
that was my own construction (`pick_dim = \a->a`, an already-blocked
`clang_Type_getSizeOf`, a bare parameter instead of an annotation). **A plant that
does not move a number is evidence about the plant until proven otherwise, and
the proof is always the same: verify the instrument read what you think it read.**
