# ENGINE-ORACLE — THE ENGINE HAD NO ORACLE AT ALL

## THE FINDING

**⇒ THE PORT's SCHEDULER's ENGINE (`tinybendygrad/schedule/rangeify.bend`'s `eng_*`) IS
**472 LINES**, IT **COMPILES**, IT **RUNS**, AND IT EMITS **14 ROWS PER FIXTURE** — **⇒ AND
NOTHING COMPARES ITS OUTPUT TO CPython.**

**MEASURED:** `grep -rln 'eng_a_s|eng_b_s|eng_fixture_rows' --include='*.py'
--include='*.rows' --include='*.sh'` ANSWERS **NOTHING** OVER THE WHOLE TREE.

**⇒ ⇒ SO THE ENGINE IS **A ROW THAT CANNOT GO RED**, WHICH IS THE TREE's OWN DOCTRINE 2
(`PASS`/`FAIL`/`SKIP`/`DEAD`/`REFUSED` — *"`DEAD` IS NOT A ZERO AND NOT A PASS"*).** **⇒ AND
THE ENGINE IS THE **MISSING LINK** THE `Device` LANE NEEDS (§3), **⇒ SO IT IS THE ROW WITH
THE MOST VALUE IN THE TREE AND IT IS **UNGUARDED**.**

## AND THE PORT's OWN FIXTURES ARE **NOT** UPSTREAM's INPUT SHAPE — **MEASURED**

**⇒ THE ENGINE's INPUT, PER UPSTREAM (`tinygrad/schedule/__init__.py:132`), IS
`prepare_rangeify(function)`'s OUTPUT — **A SINK OF AFTERs** — NOT A KERNEL GRAPH.**

**⇒ ⇒ AND CPython's OWN `get_kernel_graph` **REFUSES** BOTH OF THE PORT's TWO FIXTURES,
WITH THE EXACT ERROR TEXT:**
```
eng_a_py_out=RAISED:TypeError:'>=' not supported between instances of 'tuple' and 'int'
eng_b_py_out=RAISED:RuntimeError:UOp verification failed at 1 on Ops.NOOP dtypes.void 0 [] ()
```

**⇒ ⇒ AND **THE FIXTURES ARE NOT EVEN THE SAME GRAPH AS CPython's READING OF THEM** —
NO: **THEY ARE.** MEASURED, THE PORT's `eng_a_in` DUMP AND THE ORACLE's `eng_a_py_in` DUMP
ARE **THE SAME 14-NODE SET** (ORDER-FREE), **⇒ SO THE PORT's FIXTURES **ARE** THE GRAPHS
THE ORACLE BUILDS — **⇒ AND THEY ARE **SYNTHETIC** GRAPHS BUILT TO FIRE INDIVIDUAL RULES,
AND **CPython'S VERIFIER REFUSES THEM** — **⇒ WHICH IS WHY A COMPARISON AGAINST UPSTREAM
ON **THOSE** FIXTURES IS IMPOSSIBLE, AND SAYING SO IS THE POINT.**

## THE RIGHT FIXTURE, AND IT IS UPSTREAM's OWN

**⇒ `.agents/slop/engine/eng-oracle.py` **SPIES ON UPSTREAM's OWN CALL** TO `get_kernel_graph`
ON A REAL PROGRAM (`(4,5) = (4,3) @ (3,5)`), AND PRINTS THE EXACT GRAPH CPython HANDS THE
ENGINE, IN **THE PORT's OWN DUMP SPELLING** (`op:argkey:srcops`, JOINED BY `;`).**

**MEASURED:**
```
eng_py_in_nodes=23
eng_py_out_nodes=9
# the engine's input  census: AFTER CONST MUL PARAM PERMUTE REDUCE RESHAPE SINK STACK STORE
# the engine's output census: AFTER CALL CONST PARAM SINK
```

**⇒ ⇒ SO **THE ENGINE TURNS A 23-NODE GRAPH INTO A 9-NODE ONE**, AND THE PORT's `eng_*`
ROWS ARE NOW **COMPARABLE WITH THE ORACLE'S ROWS ROW BY ROW, NODE FOR NODE, WITH NO
TRANSLATOR** — **⇒ AND THAT IS THE MEASUREMENT THE ENGINE NEVER HAD.**

**⇒ ⇒ AND THE PORT's OWN `eng_a_s0..s6` ROWS ALREADY SHOW THE SAME SHAPE: THE PORT's
`eng_a_s6` READS `SINK:none:CONST,CALL,NOOP,NOOP,INDEX` — **A SINK OVER A CALL** — WHICH
IS THE **OUTPUT CENSUS'S SHAPE** (`AFTER CALL CONST PARAM SINK`), **⇒ SO THE PORT's ENGINE
IS PRODUCING THE RIGHT *SHAPE* ON ITS OWN FIXTURES, AND WHAT WAS MISSING IS **THE
COMPARISON THAT WOULD SAY SO.**
