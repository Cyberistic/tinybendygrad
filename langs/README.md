# langs/ — the four-lane export matrix for one Bend core

One pure f32 program, `langs/core.bend`, exported four ways and proved to agree.

```
langs/core.bend                 the export subject: matmul, softmax, cross-entropy
langs/vectors/payload.rows       the one payload every lane reads, as u32 bit patterns
langs/c/core.c                  C SOURCE, emitted by bend (regenerated by verify.sh)
langs/c/core_harness.c          the tiny C harness that links against it
langs/js/core.js                JS source, emitted by bend
langs/js/core.mjs               ES module of the pure defs, emitted by bend
langs/js/bend_core.js           the typed JS backend
langs/js/bend_core.d.ts         the typed surface of the .mjs lane
langs/wasm/                     the wasm lane: WALL.md, the shim, and a WASI host
langs/sdk/bend_sdk.ts           BendLibrarySDK: init({forceJS}), executeTask
langs/sdk/bend_wasm.ts          the wasm backend, emscripten-shaped
langs/sdk/bench.ts              min-of-5 both backends, with machine load
langs/verify.sh                 the gate: build every lane, diff every lane
langs/NOTES.md                  what Bend 2.0.34 actually does, measured
```

Run the gate:

```
./langs/verify.sh          # 0 = all lanes agree, 1 = a lane moved, 2 = the wasm wall
```

## The result

Six lanes, **byte identical**, on Apple M2 Pro / clang 21 / node 26.8.1 /
Bend 2.0.34:

| lane | what it actually is | agrees |
| --- | --- | --- |
| `bend` | `core.bend`, interpreted by the checker | yes |
| `native` | `core.bend` compiled by bend to a native binary | yes |
| `c` | `core.c` — the **C source** bend emits — compiled by clang | yes |
| `harness` | the same `core.c` linked against a separate 5-line C harness | yes |
| `js` | `core.js` — the **JS source** bend emits — run by node | yes |
| `sdk-js` | `BendLibrarySDK` on its JS backend, over `core.mjs` | yes |
| `wasm` | **cannot be built** — see `langs/wasm/WALL.md` | wall |

Every lane prints one line, and `diff` is the whole test:

```
loss=0.93064946 trace=,1064189707,1065489034,1049310003,3209900851,1064619213,3198733517,1024668472,1068413747 in=1056964608,...,1,0,
```

### Does bend emit C source? YES

This was checked before anything else was designed, because the whole shape of
lane 1 depends on it. `bend --help` says:

```
bend <file.bend> -o <out>    build a binary, or C, JS, .mjs or BendTT by extension
```

and `bend2/main.ts:363` is what implements it:

```typescript
} else if (out.endsWith(".c")) {
  fs.writeFileSync(out, Comp.compile_book(book));
}
```

So `-o core.c` is C **source**, not a binary: 7597 lines for this program, and
`grep -n 'int main' langs/c/core.c` finds the emitted `main` at line 7540. That
is why the C lane is a real compile and not a relink of bend's own output — and
why a separate C harness is possible at all (rename the emitted `main` with
`-Dmain=bend_main`, link, call it; `langs/c/core_harness.c`).

## The exported surface

This is what the `beautiful_mnist.ts` agent imports. In Bend:

```python
def core_step(images: Array<F32>, labels: Array<U32>, weights: Array<F32>) -> F32
```

and in TypeScript, on the JavaScript lane, as the default export of `core.mjs`:

```ts
core.core_step(images: number[], labels: number[], weights: number[]): number
```

(`langs/js/bend_core.js` also exposes a `coreStep(data)` convenience that takes
the flat 42-number payload and unwraps it. The example should call
`core_step` directly: it is the surface, and it is the one the gate exercises.)

| | count | meaning |
| --- | --- | --- |
| `images` | 8 f32 | BATCH=2 samples of IN=4 features |
| `labels` | 2 u32 | one class index per sample, 0..CLS-1 |
| `weights` | 32 f32 | 27 used, five padding |
| `-> F32` | 1 | the mean cross-entropy over the batch |

The weight layout, which the example needs to build a `number[]`:

```
[ 0..14]  W1   HID=3 rows of width IN+1=5     4 products then the bias
[15..26]  W2   CLS=3 rows of width HID+1=4    3 products then the bias
```

A row's **last column is its bias**, so a bias costs no separate arithmetic and
no scratch column. 27 values, padded to the 32-slot array the harness allocates.

Two details a caller must know, both measured rather than documented anywhere:

- **An `Array` is single use.** It crosses into JS as the caller's own array
  and the callee writes into it, so handing the same array to two calls makes
  the second read what the first left behind. `langs/js/bend_core.js` copies
  before every call for exactly this reason.
- **`Nat` crosses as `bigint`.** Bend's `Nat` is unary and its literals are
  `bigint` in JS. The surface above has no `Nat` in it, deliberately.

## Why the payload is bits, not decimals

Every lane reads the same `langs/vectors/payload.rows`: 42 decimal **u32 bit
patterns**, comma separated, the first 8 for images, the next 2 for labels, the
last 32 for weights. A Bend `U32` and an `F32` are both 32 bits of `Word`, so
`F32{w}` is a reinterpretation, not a conversion.

This is the single decision that makes the gate mean something. If the wire
format were decimals, C's `strtof` and JavaScript's `parseFloat`+`Math.fround`
could round one value differently and every lane would be a plausible-looking
near-miss instead of an exact answer. With bits on the wire, "the lanes agree"
is a statement about the arithmetic, which is the thing under test.

The trace is reported the same way — raw bits — so agreement is checked to the
last ulp rather than to printed precision.

`in=` in every lane's line is the parsed images and labels echoed back, so a
lane that disagreed about the payload would say so before the loss rather than
hiding inside it.

## What f32 exactness actually depends on

Measured, not assumed, and the answers are in `langs/NOTES.md`:

- **Transcendentals are fine.** `F32.exp`/`F32.log` agreed bit-for-bit across
  the C and JS lanes on every value tried. The JS lane wraps each op in
  `Math.fround`, and f64→f32 double rounding is innocuous for `+ - * /`, so
  this is a property, not luck.
- **FMA contraction would break it.** `bend` builds the native binary with
  `clang -O3` and no `-ffp-contract` flag (`main.ts:cli_build`), so on arm64 it
  may fuse `a*b+c` into an FMA and get a different f32 than every other lane.
  This lane does not trip it, but `verify.sh` passes `-ffp-contract=off` when it
  builds the C itself so the flag is never the variable under test.
- **The sum order is the definition.** The kernel accumulates products left to
  right and adds the bias last. A numpy f32 reference using the other order
  differs by 1–2 ulp on two of nine values; the loss lands 1 ulp away. Both are
  correct f32 evaluations of the same expression, which is why the gate is
  cross-lane and not against numpy.

## The wasm lane

It cannot be built, and the reason is not a missing toolchain. Every tool was
present; all of them got the build to link; and then it traps. `corpus_setup` in
the emitted C reserves `1ull << 33` — 8 GiB — before `main` runs, and wasm32 caps
linear memory at 4 GiB with a 32-bit `size_t`, so the reservation arrives as
zero and the first heap write traps.

`langs/wasm/WALL.md` has every command, every output, the four separate things
that had to be fixed before zig's `wasm32-wasi-musl` would even link, and the
one-line upstream change that would fix it. `verify.sh` reports the wall as a
`WALL` row and exits 2, so the gate never passes quietly over a missing lane.

`langs/sdk/bend_wasm.ts` is nonetheless the real emscripten-shaped glue the
contract asks for — `_malloc`, a `ccall(ident, returnType, argTypes, args)`
resolved against the module's exports, `_free`, input written through typed heap
views, both blocks released. It is the module that is missing, not the calling
convention.

## The SDK

```ts
import { BendLibrarySDK, readPayload } from "./sdk/bend_sdk.js";

const sdk = await BendLibrarySDK.init();          // wasm if it can, else js
const answer = sdk.executeTask(payload);          // number[] -> the 8 f32 bits
sdk.loss(answer);                                 // 0.93064945936203
```

`init({forceJS: true})` skips the wasm attempt, which is the switch the contract
asks for and also how the JS lane is compared against the auto lane on purpose.
`executeTask` is the only call a consumer makes and it dispatches on the backend.

It runs under Node with no build step:

```
node --experimental-strip-types langs/sdk/bench.ts
```

A browser is a manual step and is not wired here: `core.mjs` is a plain ES module
with no Node import, so importing it from a page is the whole story, and the
wasm lane would need `core.wasm` served beside it. Both are noted rather than
guessed at.

## Benchmark

`bench.ts` runs the same payload through both backends, min of 5, and prints the
machine load beside the numbers — a timing without load is a rumour, and this
machine was running several other agents while these were taken.

```
  cpu       Apple M2 Pro
  loadavg   { 3.58 6.46 10.58 }  (1m 5m 15m)
  runs      min of 5, per backend, same payload

  backend           min ms   answer bits
  sdk/js forced         0.072   1064189707,1065489034,1049310003,...
  sdk/js auto           0.055   1064189707,1065489034,1049310003,...
```

The two rows are the same backend because the wasm lane is walled, so the table
is degenerate by construction — that is the honest reading of it. The non-SDK lanes
are timed too, as whole processes, because a table with only two JS rows says
nothing about cost:

```
  core_native           1.776   (process start, run, exit)
  core_c                1.745   (process start, run, exit)
```

Those are dominated by process startup, and the payload is 42 numbers, so none
of these numbers say anything about throughput at size. They say the lanes agree
and that the JS backend costs less than a process launch. Timing a core this
small is not a benchmark; it is a smoke test with a stopwatch.
